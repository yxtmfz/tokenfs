# TokenFS：日志批处理与锁修复后的完整消融复测

本轮针对运行开销修复，保持热点、亲和、联合估值公式不变。前三张严格比较Full与移除一个模块的完整系统，第四张才与共享SIEVE比较。每条输入的同一Full同时用于四张表；原序、反序均保留，不能挑赢家拼表。

同一二进制，三种已知开发输入×五版本×两个顺序=30次无探针测速、17,280次请求，每次576×2MiB。另有此前5次带探针诊断，不混入速度表。24MiB磁盘和4MiB总捕获内存相同，三个串行逻辑消费者、cn7至既有cn13 NVMe/TCP。没有物理GPU或真实推理实验。原始读数据未做每请求哈希，另用相同二进制做480次逐请求SHA256校验，全部通过。

MiB/s以总字节除以总前台墙钟，计入控制开销；两次合并p99仅作描述，不能消除单次退步。严格通过须两个顺序各自吞吐增加、p99不增加、含后台排空吞吐不下降，并实际改变动作；P另需实际跨域放置，J另需涉及受害者价值。无5%门槛。n=2不是显著性证明，亦不是独立留出测试。

## 本次工程修复与机制

* 请求Release删除句柄后立即释放句柄/引用保护表的锁，再等待统计事务落盘，避免后台容量检查被无关统计fsync阻塞。
* 增加默认关闭的batch_policy_events，将有序决策日志并入已有统计FULL-WAL事务；全部五版本启用。缓存READY/淘汰状态仍走原有持久化路径，校验与容量限制不变。辅助日志在后台任务完成标记之前刷盘；进程崩溃前尚未到刷新点的辅助日志可能丢失，不能当作同步审计日志承诺。
* 统计事务失败后恢复增量、最大值和原事件顺序，后续事件排在其后，重试不丢失或重复。新增原生测试注入事务失败，检查日志顺序、重试、任务完成前的持久化及Release等待时句柄锁可用。

49号诊断复用原09f2二进制：移动Full打开路径均值1.911ms，SIEVE1.573ms；统计刷新0.677ms。布局锁等待均值只有0.075ms，尾部仍有远端I/O，因此不能把全部退步简单归因于锁，更不能承诺日志优化必然让所有场景获胜。

本轮保持策略不变，看到的共同加速不能充当额外策略创新点。首轮移动热点相对NoH/NoP/NoJ/SIEVE分别+4.576/+6.961/+7.325/+2.033%，但必须结合完整反序结果判断，不能只报告首轮。
