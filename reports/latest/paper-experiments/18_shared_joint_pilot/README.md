# 新亲和与热点联合：18 次小规模先导结果

**亲和出现可重复的先导提速；热点与亲和的组合也比基础共享快，但联合损失控制仍未优化成功，同容量共享 SIEVE 仍更快。**

本轮已经实际调整策略，并在 cn7→既有 cn13 NVMe/TCP 路径完成固定的 **18 次测速＋6 项逐请求内容校验**。没有启动之前建议的24次复验，没有追加样本、挑选种子或按结果改动本轮算法。18次对应6种策略、3个新种子；没有用前轮数据拼成同一实验。

## 二、策略确实改变了什么

上一轮只补齐了读取READY副本的路径。本轮P包含实际决策变化：

1. **消费者与存放位置解耦。** 某份副本即使驻留在域1，也按所有消费者的近期需求估值，避免把域0/2对它的收益漏掉。
2. **按丢失共享覆盖的损失计价。** 淘汰一份副本时，如果仍有另一份READY副本可读，该副本的共享覆盖损失按零计；最后一份副本才承担共享读取收益损失。相同原则用于准入和淘汰排序。
3. **比较放置位置。** 在每域原有配额内比较所有可行目的地，选择最大正净收益；相同净收益优先调用域。复制成本和受害数据损失都参与判断。
4. **减少执行期间重复复制。** 按对象合并在途任务，执行时重查已有可读副本，再通过原复制、校验、配额和提交重检路径落盘。

核心估值可写为：

`U(x) = max(Σg recent_reads(g,x) − 1, 0) × bytes(x) × max(remote_us_per_byte − local_us_per_byte, 0)`

`G(x,d) = U(x) − measured_copy_cost(x) − Σ victims(d) lost_shared_coverage_value(v)`

选择`G>0`的最佳目的地。这里只能把近期历史当作复用估计，不知道未来；冷启动仍使用既有先验，后续用真实I/O与复制采样更新，未注入模拟延迟。H检测到变化后修正消费者历史，直接影响迁入及驻留价值，构成可消融的时间适应与空间放置联动。Independent只关闭受害数据损失在准入及目的地分数中的计费，保留其他功能和淘汰排序。

本轮HP平均每次运行实际执行39次放置选择，其中22次选择了非调用域；通过peer读386MiB，H重置2.67次。三个种子H/P都触发，且关闭H、P或联合损失项都改变了实际复制/淘汰动作。每个种子有11–19次HP放置选择实际计入正的受害损失。不是只打开一个从未工作的开关。

P在此是一个组合策略。本轮没有把全局估值、位置选择、复制合并各自拆开；重复副本零损失分支有功能验证，不声称其独立吞吐贡献已经被测出。

## 三、为什么联合损失控制仍慢

与Independent相比，HP把复制从141.33降到78.00MiB（**−44.81%**），但把前台远端读取从381.33提高到438.67MiB（**+15.03%**），实际速率下降**3.81%**。这说明本场景下为节约复制、保护旧副本付出的远端读取代价更大，当前净收益判断未转化成速度优势。

与共享SIEVE相比，HP只少复制16MiB，却多读远端145.33MiB；守护进程CPU从4.023增至4.667秒（约+16.00%）。完整前台慢了约1.483秒，吞吐低12.67%。CPU、I/O、后台工作有重叠，不能把这些差值直接相加或认定CPU占了全部退化的某个比例。

还有一个结构性限制：三个逻辑域位于同一客户端磁盘，共享读取没有测得真实GPU拓扑差异。跨域放置在这里主要缓解分区容量限制，不能凭存放域编号获得更短的物理读取路径。PoolSIEVE2直接池化容量，天然避免这类容量碎片化。因此不应期待增加亲和计算就必然超过共享池；若论文主张GPU拓扑亲和，仍需真实不对称访问成本的证据。

源码与计账提示的下一步问题是：

- 估值将各域自己的最近128次访问直接相加，各域实际覆盖的时间长度不同，稀疏或转移消费者的旧热度可能被保留过久；不等同于同一未来收益窗口。
- 历史受益次数不能直接代表剩余复用次数。当前受害数据损失可能过高，使有用迁入被推迟。
- 每个miss检查多个目的地的元数据和价值有实际CPU成本。成本模型主要采样底层读取与复制，未完整建模控制器自身开销。
- H在这个带四请求突发、八对象热点的场景下单独不稳定。重置次数不能直接当作误触发次数，因为多个域可分别变化；需要定位具体触发时刻，不能仅凭汇总量断言每次退化原因。

这些是有依据的修正方向，不是已经独立证明的全部根因。下一版应首先统一消费者历史的时间尺度、约束陈旧受害价值，并减少重复全量规划。不能仅通过随意降低损失权重、挑选更有利工作负载来“保证”胜出。

## 四、创新性推进到哪里

本轮已从“能否读取共享副本”的基础修复，推进到“消费者收益、共享覆盖损失、等配额目的地选择与热点适应联动”的可执行候选机制，具备明确目标函数、独立开关及受控实验。

但**候选机制更完整不等于新颖性已经成立**。成本驱动协同缓存、迁移/复制和在线决策已有[TPDS 2019研究](https://grc.iit.edu/publications/wang-2019-cost-driven-f3e9/)；[OmniCache](https://www.usenix.org/conference/fast24/presentation/zhang-jian)已有协同缓存及模型驱动决策；[Preble](https://arxiv.org/abs/2407.00023)已有跨GPU KV复用与负载均衡。因此不声称首次使用共享缓存或成本函数，也没有证明理论最优/竞争比。

论文可继续研究的候选贡献应限定为：变化需求下，按共享边际收益与局部分区约束进行在线放置，并让热点证据直接更新联合决策。要成为有说服力的第二创新，仍需证明这种联动不能被更简单的同容量共享缓存替代。目前PoolSIEVE2仍更快，这一门槛尚未达到。第三个联合控制创新也未通过本轮速度检验。

## 五、控制变量与验证边界

- 同一Release二进制、相同1152MiB请求、三个新种子2801–2803、空应用缓存、前台两层O_DIRECT、相同异步复制与内容校验，无故意限速或未来信息。
- 前五组每域8MiB，共24MiB；PoolSIEVE2在域0提供共享24MiB，其他域0。总容量相同；强基线允许池化，故不受逐域预算碎片化约束。这是有意保留的强参考，不是严格逐域约束下的一字段消融。
- 简单共享、H、P、HP构成四格；H/P配对只差相应开关。HP与Independent只差联合损失开关。实际内部观测和H触发次数可随决策而改变，不能宣称运行状态轨迹完全相同。
- 三个阶段各192请求，85%选择该阶段8个热对象，15%选择新冷对象，每对象四请求突发；80%请求来自主调用域，其余均匀分布。前两阶段主域0，第三阶段主域1。策略收不到阶段标签；这是针对性合成负载，不是公开生产轨迹或真实KV张量。
- 三个种子中，每种策略各经历一次早、中、晚执行位置；不完全等同于全部六个位置的平衡。
- cn7仍是逻辑GPU/共享客户端磁盘环境，未运行CUDA、NVLink或真实推理。不能把MiB/s改写成多GPU推理提速。共享目标机缓存未清空或受控。
- 本轮没有增加无共享负对照、并发、长时间稳定性或真实GPU实验。因此只能用于筛选研究方向，不能替代最终论文证据。
