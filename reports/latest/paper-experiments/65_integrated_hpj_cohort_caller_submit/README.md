## 原因与边界

最新原版诊断中，Full 最慢6个请求有5个是首次远端读取、1个是本地读取。六请求平均29.368ms，其中 pread21.133ms、客户端打开3.902ms、布局锁等待0.002ms。共享 SIEVE 诊断还出现一次113.426ms的远端请求；这是波动现象，不能当成 Full 的策略收益或直接归因于外部负载。

此候选减少了两处统计事务的重复写入，但保留了读回调中的同步提交，并把更多统计工作合入该事务。实测不能确认净收益；没有新候选逐阶段追踪，不能断言退步就是某个单独原因。热点与亲和主要减少后续重复读取，无法免除从未读过的数据的首次远端传输。因此“缓存命中率提升”不等于“所有版本的冷请求 p99 必然下降”。

后续应优先隔离远端冷读、FUSE 数据拷贝和提交等待的成本，再针对可减少的部分修改；保持同能力基线、实际响应时间和完整失败记录。不能通过排除冷读、放宽 p99 门槛或反复重跑直至出现正值来证明提升。本轮停在预定的小规模诊断和交叉核验，不追加调参扫测。

## 验证和主线状态

候选10个原生测试目标、134个 Python 测试通过，包括提交计数持久化顺序及事务回滚计数检查。独立审计重新计算10组5760条请求、4组2304条交叉请求及2组1152条诊断请求，并核对源文件哈希、配置、最终SQLite计数、内存/磁盘预算和后台完成计数。正式测速未逐请求计算SHA；数据副本校验由现有基准执行，本轮不新增全内容正确性结论。

撤回候选后，src/main.cpp 和原生测试恢复到本轮开始的主线版本。report64 的历史8/8结果仍保留，但那是已知单一输入的两轮开发证据，不能据此宣称统计显著或普遍稳定。真实物理GPU与多GPU传输仍未验证。
