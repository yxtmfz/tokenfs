# Report68 — 热点估值的磁盘需求回放筛选

**本报告没有新增服务器测速，没有新的 MiB/s 或 p99。三种候选均未采纳，生产代码保持原保留版。** 本地模型用于筛选缺乏明显机制收益的方案，不能替代真实端到端验证。

当前 NoHotspot 是基础静态频率估值对照：仍使用近期访问频率、共享价值、测量读成本与复制成本、放置和联合准入，关闭新增的动态估值。因此，现有 H 消融检验的是动态估值增强的边际收益，不是缓存或全部热点识别的总收益。

## 本轮修改与校验

在归档候选中新增 DiskDemand 摘要：实际到达磁盘层的访问才产生磁盘复用证据，共享捕获层命中只推进时间。按对象统计返回间隔与过期，避免用全局平均连续访问长度折算所有对象。

三种候选分别为近期证据与长期预测取大值、按间隔离散程度缩减预测、只使用近期磁盘证据。均只读取已发生的请求前缀。三个原型的 RAM 排除、前缀一致性、时间衰减、历史淘汰测试通过。所有八条输入的 NoHotspot 动作计数在四种实现间完全一致，复现程序强制检查。原型尚未接入生产 FUSE 路径，也未上传服务器。

## 结论

- 磁盘需求预测候选在移动73501、73503和公开73602同时比基础频率多读远端、多复制，未达到进一步测速的筛选条件。
- 增加间隔离散惩罚仍未产生全面机制收益。
- 仅近期证据在公开三条输入上与基础频率的远端读取数、复制数相同，不能证明预测增强；移动收益有限，均匀随机减少读取但增加复制。
- 继续研究应估计“在有限驻留时间内，排除共享捕获已服务的请求后，下一次有效磁盘复用概率与间隔”。H 负责需求估值，P 负责放置，J 负责计入复制及受害者损失，不能把共同 I/O 优化算成 H 独立贡献。
- p99 继续包含首次访问。冷读关键路径需要单独诊断，不能承诺仅改变热点估值就让所有场景的 p99 下降。

## 复现与局限

运行 `python3 validation/replay.py`，需要支持 C++17 的 `c++`。程序校验 SHA 清单、编译四个估值实现、执行原型测试、复算并精确核对 screen.json。输入直接来自已使用过的报告66，不是独立确认。

模型包含三个各四对象的磁盘域和二对象共享捕获，假定复制立即完成，固定远端、本地、复制成本为21、10.5、8毫秒。没有模拟 FUSE、SQLite 持久化、实际 I/O、异步重叠、队列和争用，因此不能产出或推断吞吐与 p99。报告67已表明减少复制不保证真实提速，本轮据此未扩大远端实验。
