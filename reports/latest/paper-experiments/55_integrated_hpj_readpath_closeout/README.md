# TokenFS：元数据读取与副本原子发布修复后的完整消融复测

**本轮结论：三类负载相对共享SIEVE的实际吞吐均在两个顺序中提升，已从单一随机场景扩展到三场景。仍非所有指标达标：固定热点首轮p99有退步，H/P的部分消融存在顺序敏感性，不能称三个创新点全面成立。**

本轮针对运行开销修复，保持热点、亲和、联合估值公式不变。前三张严格比较Full与移除一个模块的完整系统，第四张才与共享SIEVE比较。每条输入的同一Full同时用于四张表；原序、反序均保留，不能挑赢家拼表。

同一二进制，三种已知开发输入×五版本×两个顺序=30次无探针测速、17,280次请求，每次576×2MiB。另有此前5次带探针诊断，不混入速度表。24MiB磁盘和4MiB总捕获内存相同，三个串行逻辑消费者、cn7至既有cn13 NVMe/TCP。没有物理GPU或真实推理实验。原始读数据未做每请求哈希，另用相同二进制做480次逐请求SHA256校验，全部通过。

MiB/s以总字节除以总前台墙钟，计入控制开销；两次合并p99仅作描述，不能消除单次退步。严格通过须两个顺序各自吞吐增加、p99不增加、含后台排空吞吐不下降，并实际改变动作；P另需实际跨域放置，J另需涉及受害者价值。无5%门槛。n=2不是显著性证明，亦不是独立留出测试。

## 本次工程修复与机制

* 请求Release删除句柄后立即释放句柄/引用保护表的锁，再等待统计事务落盘，避免后台容量检查被无关统计fsync阻塞。
* 增加默认关闭的batch_policy_events，将有序决策日志并入已有统计FULL-WAL事务；全部五版本启用。缓存READY/淘汰状态仍走原有持久化路径，校验与容量限制不变。辅助日志在后台任务完成标记之前刷盘；进程崩溃前尚未到刷新点的辅助日志可能丢失，不能当作同步审计日志承诺。
* 统计事务失败后恢复增量、最大值和原事件顺序，后续事件排在其后，重试不丢失或重复。新增原生测试注入事务失败，检查日志顺序、重试、任务完成前的持久化及Release等待时句柄锁可用。

49号诊断复用原09f2二进制：移动Full打开路径均值1.911ms，SIEVE1.573ms；统计刷新0.677ms。布局锁等待均值只有0.075ms，尾部仍有远端I/O，因此不能把全部退步简单归因于锁，更不能承诺日志优化必然让所有场景获胜。

前一日志/锁候选首轮移动热点对SIEVE+2.03%，反序却-2.47%，完整保留在50/51与52号汇总。本轮据此进一步复用三个热查询的SQL编译程序，每次重新查询当前值并在退出时reset/clear bindings；不缓存元数据结果，允许SQLite在schema变化后重新编译。跨域副本READY与规范文件的推广状态改为单个FULL-WAL事务，第二步失败或规范元数据不存在则全部回滚。所有版本共用相同路径，策略估值和缓存预算保持不变。原生测试覆盖新增、修改、删除后的查询新鲜性、schema变化、并发查询及原子发布失败/重试。共同执行层加速不能充当新的策略创新点。

## 复核与尚未完成的主张

原生10项、cn7 Python120项通过，本地增加反序一致性后121项通过。新原生测试首次错误地假定Upsert会覆盖累计read_count，实际上该接口有意保留累计计数。测试改用Upsert真正更新的size_bytes检验查询新鲜性，生产代码未为适配测试而改变；失败和重试日志保留在53号，没有失败测速被替换。此前50号的缺依赖测试失败记录也保留。测速前核验冻结源文件；反序复用完全相同二进制与前82项源码哈希，原生测试日志复用而非冒称重跑。

源码7cab2ef10f79f2371e3869fee9f8fa9440af7025，GitHub CI36528129850成功。独立复核从全部请求、SQLite、动作和后台完成计数重算速率和尾延迟，检查相同输入、字节、来源指纹和预算，伪造增益以及同时修改JSON/SQLite的成本样本均被拒绝。报告49保留诊断，50/51与52保留前一候选原序/反序及汇总；53/54保存本候选全部原始记录、冻结源码和运行脚本。该轮合计65次诊断/测速、37,440次请求和两批960次内容校验，最终表仅使用最后同一版本30次测速。
