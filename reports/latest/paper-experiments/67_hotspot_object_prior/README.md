## 原因与试验

报告66的三组移动热点中，Full总计复制199次，NoHotspot为84次。其中复制后对应完整输入仅有一轮访问的对象分别达106次和12次。原先验按重复运行次数积累，一个老热点反复返回就能将新对象先验推高；这不是新对象自身的返回证据。

本候选仅修改`src/run_reuse.h`：按不同返回对象数计先验，首次返回加一、历史淘汰减一，查询仍为O(1)。未修改亲和、联合准入、SIEVE、容量、内容校验、持久性或吞吐/p99口径。候选实现在冻结源码和补丁中，**工作分支的生产头文件与原测试已恢复为保留版本**。

移动热点73501与公开窗口73602因为已经暴露退化而用于诊断。两者各做两轮相反执行顺序，每轮执行Full、NoHotspot、NoAffinity、NoJoint、PoolSIEVE1和OldFull。OldFull使用报告64/66同一二进制；与Full配置完全一致。此为已检查输入上的开发试验，不是新独立验证，也不声称统计显著。

## 实际结果

- 新Full相对同批OldFull：移动吞吐352.371→356.065 MiB/s（+1.048%），p99 26.945→27.296 ms（+1.304%，更差）；公开吞吐89.412→89.248 MiB/s（−0.183%），p99 28.689→28.703 ms（+0.051%）。
- 热点单开关消融：移动总吞吐+1.586%，但逐轮−2.129%/+5.502%，p99两轮均更差；公开吞吐−1.552%，两轮均更差。热点严格项0/4通过。
- 移动两轮复制133→58次（−56.39%），CPU5.83→5.39秒，但远端读取290→312 MiB。减复制同时失去部分有效缓存；不能把复制量下降直接当成端到端收益。
- 公开场景Full与OldFull的动作序列相同，两轮远端读取同为3508 MiB、复制80次、CPU10.59秒。不同墙钟结果没有支持该先验在公开场景生效；保留全部时序差异，不归因为优化收益。
- 跨域放置与联合准入的全部双指标优势未保住。公开联合、公开整体SIEVE比较仍各2/2通过，其余本轮严格比较未通过。不能用正的汇总吞吐掩盖p99回退。

## 为什么仅修热点估值难以压低当前p99

[诊断JSON](diagnosis.json)逐请求核对报告66：三组移动热点的Full最慢1%（各12条）全部为首次访问。对应输入只有60/65/60个不同对象，Full远端读取72/75/71次，能够通过更好保留消除的重复远端读取仅12/10/11次。首次访问仍需读取远端，现有无预知预取的估值无法消除它们。

移动输入每阶段8个热点，磁盘能容纳12个2MiB对象，另有2对象共享捕获；大量连续复用已由所有版本共有的捕获层解决。热点估值在这组输入中的额外收益空间有限。公开输入65%–71%的请求是不同对象首次访问，热点模块同样不能消除这部分读成本。这些是当前输入的边界，不能推广成热点估值在任何负载都没有用。

后续若继续开发，应分别处理新对象过度泛化与首次读关键路径，并计入实际异步重叠/争用。先在本地机制回放验证，再冻结小样本检验。不能通过删冷请求、改p99定义、削弱消融基线、挑种子或只展示快的轮次完成目标。本次不扩大实验、不覆盖最终独立结果。
