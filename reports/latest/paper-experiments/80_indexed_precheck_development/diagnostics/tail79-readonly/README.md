# 79 五个失败比较的只读 tail 审查

只读取已下载的 79 `requests.json`、`result.json`、配置、比较回执及 SQLite；SQL 在确认 WAL 为 0 字节后以 `mode=ro&immutable=1` 读取。未连接服务器、未补跑、未改冻结源码或原始结果。339 个 raw 文件的前后 SHA 全部相同。

**结论：移动第二轮的 p99 附近全部是首次冷读；公开负载 Full 的慢尾则以重复访问为主，但现有记录不能把这些重复请求可靠标为 remote/local/RAM。** 五项失败中只有 moving/SIEVE 是 p99 失败，其余四项是吞吐失败，不能把它们一律当作尾延迟问题。

## 能定位到什么程度

每次运行有 1,152 个串行逻辑请求，nearest-rank p99 是从慢到快第 12 个请求。本审查保留最慢 12 个及其邻近第 10–14 秩，按全局 key 判断第一次/重复；不会把“该 caller 第一次”误当作全局首次。

各 case 使用空应用缓存，禁用预取，源文件均从远端开始，故某 key 的全局首次请求可根据协议推断为远端冷读。这是协议推断，不是开启 request trace 后记录的 tier。重复请求的 source tier、句柄和实际 pread 事件没有在这批速度数据中逐请求记录；不能按 25 ms/10 ms 等时延阈值打标签。

`requests.json` 能按相同 `index/key/caller` 对齐两臂的客户端时延。`metrics` 只记录整次运行的分层请求数与真实 pread 操作/字节总数；`gpu_access` 是路径/域汇总，`gpu_access_events` 无 tier/handle；`policy_events` 虽有事件顺序，却没有请求序号或事件时间，异步 READY/淘汰不能安全对齐某次读取。因此**无法把真实物理 I/O 计数映射到单个请求，也无法从现有计数唯一归因某个慢请求**。

同一个 Full 被两项失败共用时这里只列一次，避免重复计数。移动 trace 共 67 个全局首次请求、1,085 个重复请求；公开 trace 共 864 个首次、288 个重复。

|moving r2 Full|12 / 0|84 / 148 / 920|696 / 486,539,264|
|moving r2 NoHotspot|12 / 0|84 / 148 / 920|696 / 486,539,264|
|moving r2 PoolSIEVE1|12 / 0|77 / 155 / 920|696 / 486,539,264|

公开 Full 两轮的最慢 12 次均为 **33.3% 首次冷读、66.7% 重复请求**。基于汇总计数，其最慢 12 次只能界定 remote 为 4–12、local 为 0–8、RAM 为 0–2；三个区间不能独立随意组合，三层仍需合计 12。NoAffinity r2 的相应区间为 remote 11–12、local 0–1、RAM 0–1。其它表中 12/0 的 case 在这个协议下全部是远端冷读。没有把“重复未知层”伪装成“已确认重复远端”。

真实 pread 总数相同不代表远端/本地路径相同，也不代表延迟相同。本批这些 case 的 RAM 数固定，所以落到磁盘的请求总数相同，local 与 remote 的比例仍可改变。

## 同请求序号和 p99 秩并不等价

下表取 Full 恰好位于 p99 的请求，再看对照中相同序号的响应。时延单位 ms；不是将两臂各自第 12 慢请求错误当作同一请求。

|失败比较|Full p99 的 index / key|首次/重复|Full 同序号时延|对照同序号时延|对照中的慢序秩|
|---|---|---|---:|---:|---:|
|moving r2 / NoHotspot|416 / 15|首次|26.561089|26.707189|18|
|moving r2 / PoolSIEVE1|416 / 15|首次|26.561089|26.398048|13|
|public r1 / NoHotspot|512 / 55|重复|28.289912|24.635042|198|
|public r1 / NoAffinity|512 / 55|重复|28.289912|24.433809|188|
|public r2 / NoAffinity|67 / 52|重复|27.652282|24.977940|97|

例如 moving/SIEVE 的 p99 差只有 0.109362 ms，但两臂 p99 不是同一个 key：Full 第 12 慢是 index 416；SIEVE 第 12 慢是 index 96，该请求在 Full 中只有 24.286717 ms（第 53 慢）。这说明边缘顺序统计量会换样本，不能将一次 0.413% p99 回退解读为所有请求都变慢。

另一方面，public Full 的这些重复慢请求确实比相同序号的对照慢 2.67–3.86 ms，应保留问题；但当前文件不能确定它们是后端远端服务变慢、不同缓存路径、控制开销还是异步复制竞争。

## 吞吐失败的时间分解

下表对齐全部 1,152 个请求，按 key 首次/重复相加，再计入请求循环其它间隙。数值为 **Full − 对照，正值表示 Full 多花时间**，单位 ms。这是观测墙时的加法分解，不能当作互不重叠的内部 causal CPU/I/O 成本。

|比较|首次请求响应差合计|重复请求响应差合计|循环其它间隙差|整轮墙时差|
|---|---:|---:|---:|---:|
|moving r2 / NoHotspot|−20.445|+30.197|−0.012|+9.740|
|moving r2 / PoolSIEVE1|−2.866|−172.739|−0.603|−176.208|
|public r1 / NoHotspot|−37.997|+108.818|−0.953|+69.869|
|public r1 / NoAffinity|+93.823|+48.410|−0.917|+141.316|
|public r2 / NoAffinity|+276.696|−265.382|+0.089|+11.402|

- **移动 H**：两臂实际服务层汇总相同。首次冷读总计更快，但重复访问多花 30.197 ms，抵消后吞吐回退。仅改冷读 p99 并不能建立 H 的命中/估值贡献。
- **移动 SIEVE**：Full 重复访问已省下约 172.739 ms，整体吞吐提高；p99 却由不同的首次冷读占据。新缓存价值公式无法把未见过的 key 变成命中。控制路径和复制对冷读的干扰仍可间接改善，但需要下一批同批计量，不能从本次 p99 的 key 推出唯一瓶颈。
- **public H r1**：首次部分节省约 38 ms，重复部分损失约 109 ms，应该检查重复路径和后台准入时机。
- **public P r1**：首次与重复部分均负；不能只归因亲和复制。
- **public P r2**：重复请求已节省约 265 ms，却被首次冷读部分多出的约 277 ms抵消。对“局部收益没成为全局收益”有直接的观测证据，但尚不能分开远端噪声、控制和后台干扰。

## 后续优化边界

1. H/P/J 可影响重复请求的驻留、源层、复制数量/位置、规划和后台争用；应以整体墙时及逐轮 p99/drain 保留验证。不要把降低 remote 数直接等同于吞吐收益。
2. 首次未见 key 在现有无预取协议下不可由缓存决策直接消除远端读。减少前台元数据开销、无用提交及复制干扰可能间接帮助冷读，但当前证据无法证明某项就是 root cause。
3. 公平公共路径优化应给相关 Full/消融同开；不能改变 p99 口径、删除首次冷读、截去慢尾、选择改善的一轮，或按延迟阈值虚构 route。
4. 若候选 80 仍留有 tail 缺口，只有另行标注的低规模 trace 诊断才能补齐请求→句柄→tier→pread/复制时段的映射。Trace 会改变在线时序，不能替代正式速度结果。本审查没有请求或执行新 trace。
