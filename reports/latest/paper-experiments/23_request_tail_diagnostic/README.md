# 六组尾延迟诊断结果（报告23）

已完成全部 **6/6 组**，无补跑、无结果替换、无新增正式测速。结论：完整版在两个新种子上均比两种 SIEVE 更快，但 p99 在四个成对比较中全部更高。剩余慢请求主要花在实际远端读取上；本轮没有证明尾延迟缺口已经解决。

## 1. 固定设计与适用范围

- 三种策略：AdaptiveHP（报告22完整版）、PoolSIEVE1（共享 SIEVE 淘汰 + 首次访问准入）、PoolSIEVE2（共享 SIEVE 淘汰 + 二次访问准入）。均为 TokenFS 内实现，不是原 SIEVE 论文程序的直接测速。
- 原热点变化生成器，种子3221、3222；每组576×2MiB=1152MiB，三个逻辑消费者串行回放。2个种子不足以做显著性结论。
- 总缓存都为24MiB；完整版分8/8/8MiB，共享池24/0/0MiB。地址均可共享，但容量约束不同：这是系统对照，不是单变量亲和消融。
- cn7 客户端，已有 cn13 NVMe/TCP 远端挂载；未访问cn14。前台两层O_DIRECT，后台复制校验、SQLite FULL-WAL不变；远端操作系统缓存未受控。
- 两个策略头文件与报告22哈希完全相同。全部策略增加同样的可选有界内存遥测和客户端时间戳；遥测可能影响时序。
- **以下速率均为诊断数据，不替换报告22正式结果，也不与旧版本结果拼接。** 没有真实GPU、CUDA或端到端LLM推理测量。

## 3. 哪些原因已被定位

**吞吐收益来自更少的前台远端读取，但剩下的远端未命中仍然很慢。** 完整版两组前台远端读取208/230MiB，1hit为224/272MiB，2hit为314/350MiB。少读远端支持平均吞吐改善，不能自动保证最慢请求更快。

每组取最慢6次请求（上端约1%），两组共12次。分段记录如下；分段均为相同12次请求上的平均，pread属于客户端读阶段，不能与后者重复相加。

|策略|最慢12次平均响应 ms|客户端打开 ms|客户端读取 ms|实际pread ms|pread占响应|Open布局锁等待 ms|
|---|---:|---:|---:|---:|---:|---:|
|AdaptiveHP|41.105|4.241|36.529|33.596|81.7%|0.0025|
|PoolSIEVE1|37.194|3.931|32.942|30.438|81.8%|0.0028|
|PoolSIEVE2|36.602|3.272|33.065|30.970|84.6%|0.0008|

1. 三种策略这36次最慢请求全部来自远端。完整版12次中，实际pread约占响应的81.7%；最大单次响应65.97ms，其中pread累计61.29ms。不能用仅调整打分公式或布局锁来解释和解决这类I/O长尾。
2. 完整版上述请求的Open布局等待平均约0.002ms。GetAttr布局等待两组尾部均值约0.0009/0.0200ms。当前记录不支持“布局锁是主要长尾”的判断。
3. 本轮3456次Release均在客户端close返回后完成。完整版客户端close通常约0.01ms，Release内部刷指标约1.04ms（所有请求平均）。因此不能把这1ms直接加到同一次客户端close上。但它可能影响后续请求：完整版尾部请求打开阶段与前一请求Release有平均约0.83/1.11ms重叠，不能据此排除间接元数据竞争。
4. 完整版复制流水线平均约51.46ms，其中copy_file约34.86ms、源/目标校验合计约12.74ms。代码中前台pread、后台copy_file、源校验分别读取源数据，这是可以检查到的重复读取路径；它们是否都落到物理盘、各自产生多少竞争，当前记录没有测量。

## 4. 哪些还不能当成因果结论

完整版219次远端请求全部与复制流水线重叠，1hit的248次也全部重叠；没有同策略、同条件、不重叠的远端对照。因此“后台复制导致所有长尾”尚未被验证。2hit有91次不重叠的远端请求，但其准入时机、请求位置不同，也不能直接作为因果对照。

完整版有14次本地读与复制重叠，其平均pread约16.93ms；919次不重叠本地读约9.09ms。这个相关性值得继续验证，但样本和时机不均衡，仍不能当成复制竞争的确定量化效应。

两个种子的完整版吞吐收益真实记录在案，但比强1hit基线仅约0.98%，尾延迟依旧更高。没有达到“明显且全面优于SIEVE”，也没有重新验证最新版本的热点/亲和/联合各自消融。

## 5. 下一步可执行修复与小规模验证提案

优先尝试**复用前台完整读取的数据来填充共享缓存**，避免同一未命中对象被前台读一遍、后台再次取源复制和取源校验。此项是执行路径优化，不能仅据此声称新的GPU亲和创新。

实现边界：只接受不可变对象的完整、顺序、无错误读取；有界暂存；目标文件仍须重新读取并校验；内容完整和配额重新检查通过后才标记READY。部分读取、乱序、写入、故障或内存不足均回退当前路径。继续执行同样的准入、受害者价值、打开句柄保护和元数据持久化。记录真实新增内存、写入和校验成本，联合控制器不得把复制成本视为零。

为了区分“共同I/O实现变快”和“策略本身更好”，该路径必须同样提供给两个SIEVE基线；不能只给完整版更快的存储通路。

建议下一轮固定12组：三种策略×当前填充/读取复用填充×两个新种子（建议3231、3232），仍576×2MiB和24MiB缓存。正式计时关闭本轮详细遥测；运行前测试并冻结程序、输入、顺序与判据。主比较是相同新路径下完整版对两种SIEVE；每种策略的新旧路径比较用于量化工程优化。12组不能完全平衡三种策略与两种模式的运行顺序，应事先随机并轮换、如实保留限制。不得复用本轮带遥测成绩充当旧路径对照。

通过条件建议：完整版对两种同路径基线都两个种子更快、配对提升至少5%，且每种子p99不高于基线；结果不好则保留失败结论。这只是探索门槛，不是统计显著性或论文录用门槛。通过后再讨论最少量的H/P/J重新消融和代表性负载确认。

**该修复尚未实施，12组尚未运行，也未计入已批准的6组预算；需要另行确认后执行。**
