## 本轮机制证据与仍需保留的限制

热点3241：关闭共享读取时远端290MiB、复制44次、执行前copy_cost拒绝6次；开启后远端98MiB、内存304MiB、复制49次、该拒绝0次，实测吞吐提高41.62%。这次在旧对照中出现了类似的拒绝/额外远端读取问题，但不是报告25原始25次拒绝的精确复现。热点3261开启后也提高24.07%，两个热点p99均下降。

随机3262只有2MiB（1次请求）来自暂存内存，不能用直接内存命中解释全部9.97%提速。新旧控制器复制21/15次、远端566/710MiB，说明缓存准入和驻留状态也出现差异；单次运行不足以区分时间反馈、系统波动及可重复策略效应。该场景新版相对旧版p99升高3.58%，必须保留为退化项，不能说所有指标都改善。

对同能力SIEVE-1hit，热点配对提高2.86%、两次都更快且p99都更低；这是积极的小规模结果，但不足预设5%门槛。对SIEVE-2hit热点提高17.75%。随机对两种SIEVE分别提高19.48%和19.85%，p99均更低，但随机仅一个种子。

## 改动与控制变量

前台完整读取后，后台仍在为该对象构建副本期间，其他只读消费者可借用同一份不可变捕获数据。部分捕获不能暴露；借用不匹配时回退正常路径，每次借用读取再次检查已打开的源；已借用句柄发现源改变则返回错误。磁盘READY仍由原校验和提交流程发布，不能把内存可读当成磁盘已提交。

捕获对象由共享所有权固定到读取结束，所有借用者共用同一缓冲区，不重复分配；已没有后台放置任务的新请求不能继续将其当作持久内存缓存。4MiB暂存上限对全部策略相同；内存样本单列，不进入远端/本地磁盘成本估计器。报告26未提速的incremental_copy_cost保持关闭。

每组576×2MiB请求，24MiB磁盘缓存总预算、4MiB暂存预算。完整版8/8/8MiB分区，SIEVE为24/0/0MiB共享池；因此HP与SIEVE是同容量系统比较，不是仅改变亲和的一因素对照。逻辑消费者串行请求，cn7客户端与既有cn13 NVMe/TCP远端；没有物理GPU/CUDA/LLM推理。磁盘两层前台O_DIRECT、目标内容校验和SQLite FULL-WAL配置不变。详细请求探针关闭，summary中的open_ms/layout_wait_ms占位0不能解读为零开销。

## 正确性、数据审计与证据边界

7项原生测试与93项Python测试在cn7通过；源码CI36422676523成功。原生测试以同步屏障构造提交前后读取，覆盖数据内容、部分数据不可见、EOF/偏移、源替换和内存固定/释放，不靠时序睡眠碰运气。性能轮每个缓存目标有校验，但未对每个用户响应加SHA开销；这不等于逐请求端到端校验试验。

独立复核35个源码哈希、固定输入/配置/执行顺序、6912次请求及其墙钟、p99、最终SQLite全量指标、每个消费者访问次数和顺序、三层字节守恒、内存借用次数、每请求成本样本、缓存容量、复制完成及后台排空。报告器WAL只读问题已修复；之前两组诊断的原始report失败仍在报告27保留，不覆盖原退出码。
