# 08 共享副本放置

副本放置回答的是：远端已有主副本时，要不要把数据复制到某个 GPU 节点本地，以及复制到哪里。

## 1. 基本语义

当前系统采用：

```text
远端 NVMe-oF SSD：共享主副本和容量层
GPU 节点本地 SSD：热点缓存副本
```

本地副本的作用不是永久保存全部数据，而是让高频访问的 GPU 少走远端网络路径。

## 2. 共享何时出现

项目不默认假设所有 GPU 都共享同一份数据。共享只在以下场景中有意义：

- 公共 prompt 前缀被多个请求复用。
- KV Cache 被多个 GPU 或多个任务读取。
- 任务迁移后，新 GPU 继续访问旧缓存。
- 多 GPU 分片推理中，某些缓存块被不同 GPU 共同依赖。

如果每个 GPU 完全独立工作，副本放置自然退化为：

```text
谁产生、谁访问、谁本地缓存；
冷了就回到远端或被淘汰。
```

## 3. 放置决策

新增本地副本前，系统会估计：

```text
复制完成后，未来访问能省多少时间？
复制过程会占多少后台带宽？
本地空间是否足够？
这个 GPU 是否真的是近期热点访问方？
```

对应公式是 `ReplicaGain`，见 [06_cost_model.md](06_cost_model.md)。

## 4. GPU 亲和与时间窗口

TokenFS 主路径记录：

- 文件由哪个 GPU 产生。
- 哪个 GPU 长期访问最多。
- 哪个 GPU 在短时间窗口内访问最多。
- 当前亲和趋势是否发生变化。
- 目标本地副本数量。

相关字段：

```text
producer_gpu
dominant_gpu_id
recent_dominant_gpu_id
recent_read_count
affinity_trend
target_local_replica_count
affinity_state
```

这不是为了复杂化概念，而是为了避免两个错误：

```text
只看长期累计访问，导致热点已经转移但系统还不动；
只看最近几次访问，导致副本在 GPU 之间来回抖动。
```

## 5. 副本数量

副本数量不是越多越好。多个本地副本的意义是：如果多个 GPU 或多个节点都高频访问同一份远端主副本，本地副本越贴近访问方，走本地路径的机会越大。

但副本也有代价：

- 占本地 SSD。
- 占后台复制带宽。
- 增加元数据和恢复复杂度。
- 热点变化时需要清理。

因此当前策略使用上限、冷却时间和最短驻留时间控制副本数量。

## 6. 防抖动机制

防抖动是为了避免这种情况：

```text
GPU0 刚访问几次，复制到 GPU0
GPU1 又访问几次，马上复制到 GPU1
随后 GPU0 又热，继续迁回 GPU0
```

当前采用：

| 机制 | 作用 |
|---|---|
| 短窗口热度 | 识别最近热点 |
| 长窗口趋势 | 判断热点是否真的迁移 |
| 最小样本数 | 样本太少不做激进动作 |
| 冷却时间 | 刚复制或删除后暂不反复调整 |
| 最短驻留时间 | 本地副本至少保留一段时间再允许删除 |
| 副本上限 | 防止到处复制 |

## 7. 同节点 GPU 去重

如果多个 GPU 位于同一物理机器并共享同一块本地 SSD，同一个 KV Cache 不需要为每张 GPU 存一份物理副本。当前 AURA-KV 模型支持同节点副本复用，避免把 GPU 逻辑副本误当成物理重复文件。

## 8. 当前状态

Implemented：

- TokenFS 记录调用方 GPU。
- 累计访问统计。
- 短窗口访问事件。
- 多级亲和状态。
- 跨 GPU 隐藏本地副本创建。
- 本地副本表和管理工具展示。
- AURA-KV 模拟层支持共享状态、固定副本、亲和放置和 AURA-KV 策略。

- 跨物理机真实 peer 副本读取仍在模拟层。
- TokenFS 主路径未接入真实 GPU runtime。
- 副本放置未与真实 NVMe-oF 带宽队列闭环。
