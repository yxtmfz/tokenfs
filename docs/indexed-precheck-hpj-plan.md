# Indexed submission precheck development protocol

Report79 eliminated many background submissions but added 217–224 ms of foreground precheck work on each public Full run. The actual SQL scans canonical file metadata, including hundreds of remote-only objects; only a small resident subset is needed for the current capacity bound. This candidate adds opt-in partial covering indexes after successful fresh-cache eligibility checks. It keeps the SELECT and current-state policy semantics unchanged. Index maintenance costs and asynchronous decision changes remain part of the measured result; no speedup is assumed.

Use the same inspected moving_shared seed74801 and public_toolagent seed74802, 1,152 requests ×2 MiB, total disk quota24 MiB and retained capture4 MiB. All arms inherit report79 configuration including submission precheck, submission/release fences and CPU affinity[0,2,4,6]. Full,NoHotspot,NoAffinity,NoJoint differ only in their established one-flag ablations. PoolSIEVE1 retains its complete ordinary SIEVE path; it neither executes measured prechecks nor creates the new indexes on the fresh database. NoIndexedPrecheck differs from Full only in indexed_shared_precheck=false and still executes the report79 precheck.

Two rounds reverse a predetermined order (seed1050000+input seed), for24 speed runs plus576 separate content-hash requests. Fresh application cache and metadata per arm. Freeze all source, protocol and binary before timing. Complete all cases regardless of sign; no mid-batch tuning, tracing, hash timing or performance-conditioned repetition. Operational errors stop the batch and are retained.

Four primary comparisons are Full/NoHotspot,Full/NoAffinity,Full/NoJoint,Full/PoolSIEVE1. All16 scene/round/comparison pairs must have strictly higher complete-request-wall throughput, strictly lower request p99, nonregressing background-drained throughput and applicable active/changed mechanism evidence. Report every negative pair. Aggregate positivity cannot replace these gates. The four NoIndexedPrecheck comparisons are a separate implementation diagnostic, not a new policy innovation. Index activation and fallback counters, source/SQL/request consistency and equal inputs are independently audited.

This does not repair or establish causal hotspot benefits by itself. Report79 moving H and NoHotspot execute identical I/O work; a small timing advantage without a mechanism benefit cannot establish better prediction. Indexing is a common implementation optimization, not GPU placement novelty. The environment remains cn7 logical domains and serialized callers with cn13 NVMe/TCP remote storage. These inspected development inputs do not constitute independent confirmation or physical-GPU/LLM throughput measurements.
